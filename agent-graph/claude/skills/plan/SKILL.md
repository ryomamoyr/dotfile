# タスクグラフの計画と実行

自律実行の品質は、この計画の質で決まる。時間をかけてよい。

## 1. 目標を確定する

- Issue なら `gh issue view <番号>` で本文とコメントを読む
- 「何ができれば完了か」を 1〜3 行の `goal` に書く。曖昧なら着手前にユーザーに確認する

## 2. タスクに分解する

分解の原則:

- 一タスク一目的。1 つの executor が 1 回で終えられる大きさにする（目安: 変更 5 ファイル以内）
- すべてのコーディングタスクに機械検証できる `accept` を付ける。テストが無ければ「テストを書くタスク」を先に置く
- `scope` で触ってよいファイルを限定する。広い scope は失敗の温床
- `outputs` に成果物のパスを書く。下流はそれを `inputs` として受け取る
- 独立なタスクは依存を付けず並列にする。依存は本当に必要なものだけ
- 人が読む文書は HTML（`docs/human/`）、エージェントが読む文書は md（`docs/agents/`）
- 深さは 3 程度まで。深くなるなら分け方が悪い

executor の使い分け:

| executor | 用途 | 注意 |
| --- | --- | --- |
| `codex` | 実装・修正・テスト・リファクタ | `accept` と `scope` が必須。レビューは自動で付く |
| `doc-light` | 150 行以下の文書 1 ファイル | `accept` は存在確認や lint でよい（例: `test -s docs/agents/x.md`） |
| `doc-heavy` | 長い文書・複数ファイル・HTML | 同上 |
| `human` | 承認ゲート | PR の直前に必ず 1 つ置く |
| `pr` | 統合ブランチから PR を作る | 最終ノード。他の全タスクの下流に置く |

## 3. tasks.yaml を書く

`agr init --session <識別子>` で雛形が `.agents/graph/<識別子>/tasks.yaml` に置かれる。それを書き換える。

```bash
agr init     --session <識別子>
agr validate --session <識別子>
```

エラーが出たら直す。`accept` 無しや循環依存は通らない。

## 4. 実行を起動する

```bash
agr launch --session <識別子> --max-parallel 3
```

- スケジューラは herdr の別 tab で動く。あなたの Bash は塞がれない。エージェントも仕事ごとに tab が作られ、done なら自動で閉じる
- 進捗は `agr status --session <識別子>` とダッシュボード（`agd` で起動）で見る
- 判断待ち（`waiting_human` / `conflict`）が出たら、理由を読んでユーザーに要点を伝える。決めるのはユーザー
- スケジューラが止まっても状態は残る。同じコマンドで続きから再開できる

## 5. 終了時

- `.agents/graph/<識別子>/report.md` を読み、ユーザーに「何が完了し、何が判断待ちで、PR はどこか」を報告する
- 失敗が残っていれば、原因を 1 行ずつ添える。原因が分解の悪さなら tasks.yaml を直して再実行する
